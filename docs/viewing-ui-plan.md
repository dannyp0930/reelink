# 내 기록 UI 구현 계획

기준일: 2026-09-16. 사용자가 승인한 리스트·캘린더 구조를 따른다. A·B·C1·C2·C3·D를 완료했다. 다음은 E 캘린더이며 실제 계정 통합 검증은 F에 남아 있다. 구현·검증 결과는 [작업 현황](project-status.md)에 기록한다.

같은 날 공유한 [관람 방식 설계](chatgpt-conversation://6aa3af4d-d774-83ee-b827-a9ab95b3ebfa)의 제공된 대화 내용을 반영했다. 사용자는 연도·시간이 관람한 연월일·시각임을 확인했고 개봉연도·러닝타임은 TMDB 정보로 표시하도록 요청했다. 참고 대화의 타사 앱 사례·통계·지도 예시는 구현 근거나 이번 범위로 확대하지 않는다.

## 확정한 범위

- 내 기록 하나를 리스트와 캘린더로 전환한다. 둘은 같은 관람 회차를 표시하고 상세·수정 화면을 공유한다.
- 리스트는 포스터·제목·내 평점·관람일과 입력한 시각·관람 유형·장소를 보여준다. 캘린더는 월별 날짜 칸에 포스터와 추가 기록 수를 표시한다. 극장·OTT·기타는 같은 관람 기록의 분류이며 별도 목록이나 달력을 만들지 않는다.
- 날짜를 선택하면 해당 날짜의 기록 전부를 확인한다. 날짜 옆 기록 추가는 관람일을 미리 채운다.
- 평점 API는 0~5점, 0.5점 단위이며 미평가는 별도 값이다. 작성 UI는 별 선택만 표시한다. 선택한 별을 다시 누르거나 Delete 키로 미평가로 해제하며 숫자 설명·0점·미평가 버튼은 두지 않는다. UI에서 0점 직접 선택은 제외하되 기존 0점 기록과 API 계약은 유지한다. 보기 전환 시 평점 필터를 유지한다.
- 검색 → 영화 선택 → 관람 정보 입력 → 저장 → 상세 흐름을 사용한다. 검색과 입력 폼을 한 화면에 길게 펼치지 않는다.
- 관람일은 연월일을 입력하고 시각은 선택 입력으로 둔다. 영화의 개봉연도·러닝타임은 TMDB 메타데이터이며 관람일·시각과 구분한다.
- 관람 유형은 극장·OTT·기타로 나누고 선택한 유형의 상세 입력만 표시한다. 극장은 내부 Cinema 검색·선택, OTT는 플랫폼 선택, 기타는 분류 선택·직접 입력을 제공한다.
- 상세에서 돌아오면 이전 보기·선택 월·필터·목록 위치를 복원한다. 모바일은 세로 배치, 데스크톱 캘린더는 달력과 선택 날짜 기록을 좌우로 배치한다.
- 불필요한 사용법 문구와 검색 버튼은 다시 넣지 않는다. 입력 라벨·필수 조건·오류·로딩·저장 결과 안내는 유지한다.
- Repov를 참고하되 영화 관람 기록에 집중한다. 소셜·지도·갤러리 보기·추천·새 이미지 업로드는 이번 범위가 아니다.

## 화면과 상태 계약

아래 URL과 query 이름은 구현 제안이다. 단계 C에서 API 계약과 함께 확정한다.

| 화면 | 제안 URL | 상태 |
| --- | --- | --- |
| 리스트 | `/viewings?view=list&rating=all&sort=newest` | 평점 필터·정렬·페이지 |
| 캘린더 | `/viewings?view=calendar&month=2026-09&date=2026-09-11&rating=all` | 월·선택 날짜·평점 필터 |
| 새 기록 | `/viewings/new?watchedOn=2026-09-11` | 검색과 입력 단계, 작성 초안 |
| 상세 | `/viewings/:id` | 회차 한 건, 돌아갈 보기 |
| 수정 | `/viewings/:id/edit` | 기존 값, 수정 중인 초안 |

- 첫 진입 기본 보기는 우선 리스트로 제안한다. 다음 방문 기본 보기와 무관하게 상세 왕복에서는 이전 보기를 복원한다.
- 조회 조건은 URL에 둔다. 메모·작성 초안·인증 정보는 URL에 넣지 않는다. 필터가 바뀌면 페이지를 초기화하고 캘린더로 전환할 때 목록 정렬은 보관하되 날짜 순서를 흐트러뜨리지 않는다.
- 돌아갈 주소는 허용된 내부 경로만 사용한다. 직접 상세 URL로 진입했으면 내 기록으로 돌아간다.
- 새 기록과 수정 폼은 공통 입력 구조를 쓴다. 영화 변경 시 관람일·시각·유형·상세·평점·메모를 보존한다.
- 초안은 탭 단위 `sessionStorage`에 저장한다. 저장소를 사용할 수 없을 때는 메모리로 내부 이동을 보완하고 새로고침 전 복사를 안내한다. 사용자·작성/수정 대상별로 분리하고 저장·명시적 폐기·로그아웃·계정 변경 시 정리한다. 도입 시 메모가 해당 탭에 남는 범위를 설명한다. 영구 `localStorage` 보관이나 오프라인 동기화는 추가하지 않는다.
- `beforeunload`만으로 앱 내부 이동과 모바일 종료를 보호했다고 보지 않는다. 내부 뒤로가기·새로고침·브라우저 뒤로가기·로그인 만료를 따로 검증한다.

## 관람 유형과 입력 흐름

Impeccable의 Operate 관점에서 기록 한 건을 빠르게 남기는 데 집중한다. 아래는 승인된 기능을 배치한 구조이며 색상·타이포·컴포넌트 모양을 확정한 시안은 아니다. 화면 라벨은 `관람 유형`으로 제안한다.

```text
선택한 영화 · 개봉연도 · 러닝타임
관람일 [연월일]  시각 [시:분, 선택]
관람 유형 [극장] [OTT] [기타]
  극장 → 극장 검색·선택 / 상영관 / 포맷
  OTT  → 플랫폼 선택 / 목록에 없으면 직접 입력
  기타 → Blu-ray·DVD / TV 방송 / 기내 / 영화제·야외상영 / 직접 입력
별점
메모
저장
```

- 날짜 외에 시각·관람 유형·장소 상세는 비워도 저장할 수 있게 제안한다. 시각 미입력은 `null`이며 자정 `00:00`과 다르다. 과거 기록에 현재 시각을 자동으로 채우지 않는다.
- 극장 검색과 선택은 D단계에서 단일 combobox로 합친다. 별도 검색 input과 select를 연달아 조작하게 두지 않는다. 결과에는 지점명과 구분에 필요한 주소·휴폐업 상태를 표시한다. 자주 쓰는 극장부터 검증해 등록하며 전국 데이터 선적재·지도 API·지도 화면은 이번 범위에서 제외한다. 등록되지 않은 극장은 미지정으로 저장하고 메모를 남길 수 있다. 최소 데이터 등록 절차는 검색 도입과 함께 정한다.
- OTT 플랫폼은 Netflix·Disney+·TVING·WATCHA·Wavve 등의 선택 후보와 직접 입력으로 시작한다. 이는 사용자가 본 플랫폼을 기록하는 기능이다. 제공 여부 검색·자동 추천·OTT 로그인 연동이 아니며 추가 OTT API 키는 필요하지 않다.
- 상영관은 `3관`, 포맷은 `IMAX`처럼 구분한다. 선택 입력이며 포맷별 통계는 후속 작업이다. 영화제라도 실제 극장에서 봤으면 극장을 선택할 수 있다.
- 유형 전환 중 같은 폼의 기존 입력은 임시 보존하되 저장할 때는 현재 유형의 필드만 보낸다. 수정에서 유형을 바꾸면 이전 유형의 DB 필드는 같은 요청에서 비운다. Backend도 유형과 필드 조합을 검사한다.

### 데이터 계약 초안

C1·C2에서 아래 저장 필드와 migration을 구현했다. 실제 입력 제한과 보강 동작은 API 문서와 테스트를 따른다. Frontend의 시각·유형별 입력은 D에서 연결한다.

| 대상 | 제안 | 원칙 |
| --- | --- | --- |
| MovieViewing | 기존 watchedOn + nullable watchedTime (`HH:mm`) | 날짜와 현지 시각을 분리하고 UTC 변환으로 달력 날짜를 이동시키지 않음 |
| MovieViewing | nullable viewingType: THEATER / STREAMING / OTHER | 미지정과 OTHER를 구분, 유형을 강제 추정하지 않음 |
| THEATER 상세 | 기존 cinemaId·auditorium + nullable screeningFormat | 내부 극장 ID 재사용, 장소·상영관·포맷 모두 선택값 |
| STREAMING 상세 | nullable streamingService | 작은 선택 목록과 길이 제한 직접 입력, 플랫폼별 테이블 불필요 |
| OTHER 상세 | nullable viewingDetail | 정해진 선택 후보 또는 길이 제한 직접 입력 |
| Movie | 기존 releaseDate + nullable runtimeMinutes·posterPath | 개봉연도는 releaseDate에서 표시, 러닝타임은 관람 소요 시간이 아님 |

- 시각은 `00:00`~`23:59`의 분 단위로 검사한다. 기록 당시 현지 벽시계 시각을 보존하며 절대 시점으로 변환하지 않는다. 시간대 간 시각 비교·알림은 이번 범위가 아니다.
- 기존 cinemaId가 있는 기록은 THEATER로 이관하는 안을 검증한다. cinemaId 없는 기록은 OTT·기타로 추정하지 않고 유형을 비워 둔다. 기존 auditorium·평점·날짜·메모는 삭제하지 않으며 애매한 기존 값은 수정 전까지 보존한다.
- PATCH에서 생략은 유지, `null`은 비우기 규칙을 유지한다. 유형 변경과 맞지 않는 상세값은 거부하고 필요한 비우기를 원자적으로 처리한다. 구버전 요청·기존 미지정 기록의 호환성을 함께 검증한다.
- TMDB 검색 결과마다 상세 API를 추가 호출하지 않는다. 검색은 기존 개봉일을 재사용하고 영화 선택 시 상세 정보로 러닝타임·포스터를 보강한다. 값 없음·유효하지 않은 값은 미상으로 처리하며 정보 누락 때문에 관람 저장을 막지 않는다. 기존 영화의 제한적 보강만 수행하고 전체 일괄 갱신은 보류한다.

| A | 기존 관람 작성 검증 완료 | Astra high | 기존 범위 통과, 새 시각·유형 기능은 미검증 |
| B | Repov 근거·조건부 입력 화면 설계 | Astra high | 실제 참고 화면, 유형 전환·빈 값·모바일 흐름 정리 |

### A. 기존 검증 완료

`scripts/check-viewing-ui.cjs`의 극장 locator와 화면 이탈 경고 처리를 복구했고 기존 폼 검증을 통과했다. 별 아래 버튼 제거 후 재클릭·Delete 해제와 미평가 저장도 확인했다. 상세 근거는 작업 현황을 따른다.

새 시각·관람 유형은 이 통과 범위에 포함되지 않는다. 구현 후 1280×844와 390×844에서 각 유형의 선택·전환·저장·수정, 미지정, 자정·윤년·연도 경계, 플랫폼 직접 입력, 메타데이터 누락을 추가 검증한다. UI 테스트는 대체 API를 사용하며 개인 DB에 임의 기록을 만들지 않는다.

### B. 디자인 근거 확정

2026-09-15에 [Repov 공식 소개](https://page.repov.me/)의 영화 검색·캘린더·타임라인·상세 화면을 확인했다. 포스터 중심 행, 간결한 필터, 같은 기록의 보기 전환을 참고했다. 홍보 이미지의 파란 배경을 앱 색상으로 옮기지 않았다.

사용자는 이미지 시안 대신 실제 앱에 바로 구현하는 방식을 선택했다. 이번 화면은 기존 밝은·어두운 중립색을 유지한다. `frontend/DESIGN.md`는 현재 구현의 참고 문서이며 최종 브랜드 디자인 승인으로 취급하지 않는다. 화면별 설계 근거는 `frontend/.impeccable/surfaces/app-viewings.md`에 남긴다.

### C. 데이터부터 화면 요구를 충족

C1~C3 구현 완료. 아래 항목의 실제 조회 계약은 [관람 기록 조회 API](viewings-api.md)를 따른다. `month`, `rating`, `sort`, `page`, `limit`과 `{ items, page, limit, totalItems, totalPages }` 응답을 확정했다. 기본 50건·최대 100건이며 `sort=oldest`로 날짜·시각 오름차순, 시각 미입력 마지막을 제공한다. 목록은 한 페이지 20건을 표시하며 필터·정렬·페이지를 URL과 연결했다. 월별 모든 페이지 조회는 E에서 구현한다.

- C1 → C2 → C3 순서로 나눈다. C1에서 위 관람 계약과 migration·이전 기록 호환성을 먼저 검증하고 C2에서 TMDB 상세·극장 검색을 보강한다. C3에서 아래 조회·페이지 계약을 확정한다. 각 단계는 관련 API 문서와 테스트를 함께 갱신한다.
- 포스터는 Backend가 TMDB 상세 응답에서 검증한 상대 경로를 nullable 필드로 저장하는 안을 우선 검토한다. CDN 주소는 서버에서 조합한다. 브라우저가 보낸 임의 URL은 저장하지 않는다.
- 포스터 없는 기존 영화도 계속 조회·작성 가능해야 한다. 재선택 시 제한적으로 보강하는 방식을 검토하고 전체 영화 자동 보강 작업은 만들지 않는다. 기록을 볼 때 영화마다 TMDB를 호출하지 않는다.
- 목록·상세 응답은 필요한 영화·극장 정보를 명시적으로 선택한다. 새 schema 변경은 새 migration으로 추가하고 기존 migration을 고치지 않는다.
- `GET /viewings`에 월 범위, 정확한 평점 또는 미평가, 최신순·평점순, 제한된 페이지 조회를 설계한다. 입력 `rating`과 저장 `ratingHalfStars` 변환 규칙을 유지한다.
- 평점 동점은 관람일·id로 안정적으로 정렬한다. 미평가가 섞인 평점순에서는 마지막에 둔다. 필터·정렬·페이지 처리는 서버에서 수행한다.
- 최근 50건을 잘라 캘린더로 사용하지 않는다. 월 범위로 조회하고 여러 페이지면 전부 수집하거나 집계·날짜별 조회로 나눈다. 전부 받지 못하면 완료된 달력처럼 표시하지 않는다.
- 월은 관람 날짜 기준으로 계산한다. 날짜 전용 값을 브라우저 시간대 때문에 전날·다음 날로 이동시키지 않는다.
- 응답 형태를 바꾸면 임시 화면과 테스트도 함께 갱신한다. 페이지 방식·상한·월 조회 응답은 구현 전 테스트 사례와 함께 확정한다.

### D. 기록 화면 분리

목록·작성·상세·수정 route, 삭제 확인, 유형별 입력, 초안 복원과 목록 복귀를 구현했다. 최종 테스트 결과와 남은 제약은 작업 현황을 따른다. 아래는 유지할 동작 계약이다.

내 기록, 작성, 상세, 수정 route를 만든다. 작성·수정은 위 관람 유형 입력을 공유하고 상세는 입력한 시각·유형·장소와 TMDB 영화 정보를 구분해 보여준다. 비로그인 직접 접근과 API 401 처리를 일관되게 연결한다. 기존 400ms debounce·한글 조합·늦은 검색 응답 무시를 유지한다.

새 기록은 저장 성공 후 상세로 이동한다. 오류면 입력을 유지한다. 수정은 기존 값을 불러온 뒤 PATCH하고 삭제는 확인 후 DELETE한다. DELETE의 204 응답을 JSON으로 읽지 않도록 기존 요청 함수를 최소 범위로 보강한다. 이중 클릭을 막되 다른 회차의 정상적인 재관람 기록을 중복으로 오판하지 않는다.

삭제 실패 시 기록을 남기고 성공한 뒤에만 목록·달력을 갱신한다. 다른 계정이나 없는 기록은 기존 API의 404 경계를 유지한다. 새 상태 관리 라이브러리는 필요가 확인되기 전에는 추가하지 않는다.

### E. 캘린더와 평점별 보기

월 이동, 날짜 선택, 해당 날짜 기록 목록, 날짜가 채워진 새 기록을 연결한다. 하루 여러 건은 대표 포스터와 추가 건수로 표시한다. 대표 포스터 선택 규칙은 일관되게 정하고 날짜 목록에서는 모든 회차를 보여준다.

극장·OTT·기타·기존 유형 미지정을 모두 같은 날짜 기준으로 조회한다. 날짜별 목록은 시각이 있으면 표시한다. C3에서 같은 날짜의 시각 오름차순, 미입력 마지막, 동률은 id 오름차순으로 확정했다. 미입력을 자정 관람으로 취급하지 않는다. 관람 유형별 통계·추가 필터는 이번 범위가 아니다.

리스트와 캘린더는 정확한 평점·미평가 필터를 공유한다. 필터가 걸린 상태를 항상 보여주고 결과 없음과 기록 자체 없음은 구분한다. 영화별 한 건으로 합치지 않으므로 대표 평점 정책은 이번 구현에 필요하지 않다. 영화별 모아보기를 추가할 때만 최근 평가·평균 중 무엇을 쓸지 별도 결정한다.

390px 화면에서 달력 7열을 유지하고 날짜 이름·선택 상태·기록 수를 스크린리더에도 제공한다. 키보드로 날짜·월 이동과 기록 열기가 가능해야 한다. 긴 제목, 이미지 실패, 한 달 50건 초과, 같은 날 다수 관람, 윤년·연도 전환을 검증한다.

### F. 통합 검증과 마감

Impeccable `critique`·범위별 `audit`·필요한 `polish` 후 web-design-guidelines와 Playwright를 수행한다. 규칙 검사 결과가 비어 있어도 디자인 검토·기능 테스트를 대신하지 않는다. 자동 hook 승인은 사용자 확인 사항이며 승인되지 않았으면 수동 검사로 구분한다.

실제 계정 검증은 사용자가 로그인한 상태에서 기록 생성·새로고침·수정·삭제·로그아웃을 확인한다. 테스트 기록을 만들거나 지울 때 대상을 명확히 합의한다. TMDB 공식 로고·출처 표기를 확인하고 백업·복원, HTTPS·cookie·요청 제한 등 개인 배포 점검은 배포 단계에서 수행한다.

## 단계별 검증과 작업량 관리

- Frontend 변경: 관련 테스트 → `pnpm --dir frontend lint` → `pnpm --dir frontend build` → 데스크톱·모바일 브라우저 검증.
- Backend 변경: 관련 E2E → `pnpm --dir backend lint` → `pnpm --dir backend test` → `pnpm --dir backend test:e2e` → `pnpm --dir backend build`.
- 보안 경계 변경: 제공되는 경우 security-diff-scan, 없으면 미실행을 명시하고 변경 경계를 직접 검토한다.
- 이 명령들은 후속 검증 계획이다. 이 문서를 작성하면서 다시 통과한 명령으로 취급하지 않는다.
- 한 단계 안에서도 테스트 정리·API·화면을 검증 가능한 작업 단위로 끊는다. 전체 저장소 재조사, 중복 감사, 불필요한 이미지 생성으로 토큰을 쓰지 않는다. 상위 추론 강도가 필요한 문제가 남으면 근거를 설명하고 전환 여부를 묻는다.
- 작업 종료 시 현황·남은 항목·실행한 명령을 갱신한다. 커밋·푸시는 사용자가 요청할 때만 한다. 프론트 3002, Backend 3001을 사용하며 다른 작업의 3000은 건드리지 않는다.

## 이후 범위

관람 기록 마감 → 극장 데이터 관리 → 수동 굿즈 등록·제보·승인 → 개인 배포 순서다. 굿즈 source 조사·필드 정의는 기존 문서를 유지한다. 자동 수집·알림은 허용 범위와 실제 필요가 확인된 뒤 별도 착수한다.
